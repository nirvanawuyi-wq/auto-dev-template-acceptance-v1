## 行动清单（直接照着做）

用法：从上往下逐项做。

- `[...]` 方括号里的内容要换成你自己的。
- 代码块里的命令按上下文使用；3.5.2 的图是示意。**可复用的系统规则与运行模板统一维护在第 3 节**（唯一权威源）。**提示词统一放在每一步的第 7 块**，动作里只写"用提示词 `P-xx`"。
- 负责人：**我** 你自己动手，**AI** 交给 AI，**我 + AI** 两边配合，**（需要等待）** 需要时间的项。动作里的【我】【AI】【我 + AI】标签是同一个意思。
- 这一节是"操作视图"。第 2 节是同一流程的"阶段视图"（解释为什么这样排），可复用模板在第 3 节。
- 云端相关步骤是 A1、A2、D1、D3、E1～E3、F1，细节在 3.5。执行器相关的未验证点统一记到项目的 `docs/field-notes.md`（你自己建），冒烟顺序见 3.5.5。

### 每一步的结构（7 块）

每一步的开头先有一行元信息：**层级**（一次性 / 每项目 / 每批次）｜**主负责**｜**前置**（哪些步骤要先完成）｜**下游**（谁要用这一步的产物）。然后是 7 块，没有内容的块直接省略：

1. **前置条件：** 可勾选，开做之前必须成立的事。
2. **动作：** 按顺序编号，每条前面标负责人；命令放在代码块里；提示词只写编号，正文在第 7 块。
3. **完成标准：** 可勾选，逐条核对；达到才算这一步做完。
4. **出错怎么办：** 现象 → 归谁处理 → 怎么处理，含重试上限。
5. **产出与证据：** 产出的文件路径，以及要记下的证据。
6. **待验证：** 只列需要记进 `docs/field-notes.md` 核对的点。
7. **提示词：** 本步用到的全部提示词，每条一个编号（`P-阶段步骤-用途`）。提示词里引用手册内容时写"第 3.x 节""附录 B.x"。

> 注意：附录 B 的演练项也叫 C1～C5（见 E3），与本清单的步骤编号 C1～C4 无关，E3 里写作"演练 C1～C5"。

### A. 一次性底座（做过就跳过）

> A 阶段每个人、每台服务器只做一次；之后的新项目从 B1 开始。第一次做时，A1 可以穿插在 B～C 阶段之间，最晚在 D3 之前完成。

#### A1：账号与服务器——开机、装工具、登录、装 Cezar

**层级：** 一次性（换服务器或换服务商时重做）｜**主负责：** 我｜**前置：** 无｜**下游：** A2、D3

**① 前置条件**

- [ ] 已决定用 Cezar 版（选型依据见文件开头）。
- [ ] 有云服务商账号，可以开通海外服务器（规格见 3.5.1）。
- [ ] 有 GitHub 机器账号（创建方式与令牌范围见 3.5.1）。

**② 动作**

1. 【我】选定云服务商，开通海外 Cezar 服务器（规格见 3.5.1，它不走产品的 ICP 备案流程）。开到管理用户和无 sudo 的 `agent` 用户均能 ssh 登录为止。支持 cloud-init 的话，可一次建好这两个用户，并预装 `git`、`gh`、Node 20+、pnpm。**初始化脚本里不放令牌和登录信息。**
2. 【我】装工具并登录。系统依赖缺失时由管理用户补装。以 `agent` 登录，若通过 npm 全局安装 AI 命令行，先执行 `npm config set prefix "$HOME/.local"`，并把 `$HOME/.local/bin` 加入该用户的 `PATH`。登录干活和审查工具（需要时用各自的设备码），GitHub 则用机器账号的令牌执行 `gh auth login --with-token`（范围见 3.5.1）。
   - 机器账号要到 D3 才被邀请进仓库，在此之前令牌没有任何仓库权限，所以工具登录可以提前到这里，不必等 `main-lock` 生效【待核对】。
3. 【我】装 Cezar。由有 sudo 的管理用户执行固定稳定版本 `npx cezar-run@x.y.z server-install --platform ubuntu-vps`（把 `x.y.z` 换为选定版本）。服务应以 `agent` 运行，安装器如何指定用户见 3.5.1。把 `CEZ_WORKFLOW_WEBHOOKS=1` 和通知地址放进 Cezar 服务读取的仓库外环境文件，重载服务后用手机和电脑登入。驾驶舱只经 Tailscale 或 IP 白名单访问。仓库的登记留到 D3。

**③ 完成标准**

- [ ] 云服务商已选定，管理用户和 `agent` 均可 ssh 登录。
- [ ] 以 `agent` 身份，干活和审查两款 AI 工具、机器账号的 `gh` 均已登录。
- [ ] Cezar 按系统服务运行，服务身份为 `agent`；手机和电脑都能登入驾驶舱。

**⑤ 产出与证据**

- 选定的 Cezar 版本号 `x.y.z`（记下来，后面所有 `npx cezar-run@x.y.z` 命令都用它）。

### B. 开项目

#### B1：建仓库、存需求原文、放入手册、启动 AI 命令行

**层级：** 每项目｜**主负责：** 我｜**前置：** 无｜**下游：** C1

**① 前置条件**

- [ ] 你选用的 AI Agent 命令行（Codex、Claude Code、Gemini CLI 等任选）和 Git 已装好。
- [ ] **账号前提已定：** GitHub 的合并规则集是"没过检查就不能合并"的唯一硬关卡。个人账号的**私有仓库需要 GitHub Pro**（免费版规则集不生效），否则只能把仓库设为公开。现在就定，不要等到 E3 才发现挡不住。

**② 动作**

1. 【我】初始化本地仓库：

   ```
   mkdir [项目名]
   cd [项目名]
   git init -b main
   mkdir docs
   ```

2. 【我】**第一时间把 `.gitignore` 锁死。** 在根目录创建 `.gitignore`，至少写入：

   ```
   .env
   .env.*
   !.env.example
   *.local
   node_modules/
   ```

3. 【我】到 GitHub 新建一个空仓库，关联并推送初始提交：

   ```
   git add .gitignore
   git commit -m "chore: init repo and gitignore"
   git remote add origin [仓库地址]
   git push -u origin main
   ```

   后续自动化流程围绕 GitHub PR，必须先有远程仓库和默认分支 `main`；提前提交 `.gitignore` 可以避免后续误把密钥推上去。
4. 【我】把你的需求原话直接粘贴进 `docs/requirements.md`，不用整理。
5. 【我】把本手册复制为 `docs/workflow-manual.md`（工程护栏的实施规格在其中的附录 B，不用另外复制文件）。后面提示词里的"第 3.x 节"和"附录 B"都指这份文件：新开的 AI 会话看不到你电脑上的其他文件，不放进项目它就只能自己猜格式。
6. 【我】在项目文件夹里启动你选用的 AI Agent 命令行（例如 `codex`、`claude`、`gemini`），按该工具的方式切换模型（多数工具是在会话里输入 `/model`），选**你能用到的最强模型**。
   - 如果这个流程里要换不同工具分别写计划和评审（见 C2、C3），现在不用管，到时再开新会话。
   - 如果产品想法本身还很模糊，先用 BMAD 把产品设计做完，再回到这里。需求已经具体就不用它。

**③ 完成标准**

- [ ] GitHub 上有远程仓库，默认分支 `main` 上已有 `.gitignore` 的初始提交。
- [ ] 账号前提（私有仓库需 Pro，或改为公开）已确认。
- [ ] 项目里有 `docs/requirements.md`（需求原话）和 `docs/workflow-manual.md`（本手册副本）。
- [ ] AI Agent 命令行已在项目文件夹里启动，当前模型是你能用到的最强模型。

### C. 需求到计划

#### C1：需求澄清——出问卷、答问卷

**层级：** 每项目｜**主负责：** AI 出题、我作答｜**前置：** B1｜**下游：** C2

**② 动作**

1. 【AI】用提示词 `P-C1-ask` 读 `docs/requirements.md`，逐项追问，把问卷写入 `docs/questionnaire.md`。grill-me 是某些工具里的技能名，没装也能用，换任何 AI Agent 工具都一样：这段话本身就是追问规则。
2. 【我】打开 `docs/questionnaire.md`，在每题的"我的答案："后面填写。同意推荐答案就写"同意"。
3. 【我 + AI】填完回到 AI Agent 会话，用提示词 `P-C1-check`，让 AI 只告诉你还有哪些新的歧义或矛盾。有就补答，再问一次。

**③ 完成标准**

- [ ] 生成 `docs/questionnaire.md`：问题一次给全，每题带推荐答案和"我的答案："一行，并包含四个小故事和内容权限的问题。
- [ ] `docs/questionnaire.md` 每题都已填写答案。
- [ ] AI 回复"没有"新的歧义或矛盾。

**⑤ 产出与证据**

- `docs/questionnaire.md`（含你的答案）。

**⑦ 提示词**

`P-C1-ask`（动作 1，AI 读需求后追问）：

```
读 docs/requirements.md。用 grill-me 的方式就这个项目逐项追问我，直到没有模糊点。
要求：
1. 把所有问题整理成一份问卷，一次给我，不要一问一答。
2. 每题附上你的推荐答案和理由。
3. 本轮聚焦产品与业务边界：核心用户路径、前后端范围边界、异常情况的默认兜底规则、不可逆或高风险操作（如真实扣费、数据永久写入、对外发信、主网交易）的业务规则。具体云服务和技术选型留到下一轮方案阶段，这里先不展开。
4. [前端要在后期打磨的话保留这条：前端先按朴素版处理，不要追问前端视觉细节。]
5. 把问卷写入 docs/questionnaire.md，每题下面留一行"我的答案："。
6. 对每条核心功能，给我讲四个小故事：一个没有权限的人来操作；同一件事发生两次；事情做到一半中断；上线一周后才发现做错了。每个故事都告诉我：用户会看到什么、我能不能发现、还能不能补救。把必须由我决定的地方圈出来，每处给一个推荐答案。
7. 内容与权限必须问清：用户提交的内容默认谁能看、谁能公开、发错了能撤回到什么程度；哪些内容一旦发出（如永久发布）就无法收回。如果项目含 AI 判断（识别、分类、提取），再问清：AI 拿不准、识别服务没响应、用户明确说"不要"时，各自怎么处理。
```

`P-C1-check`（动作 3，你答完问卷后）：

```
我已回答完 docs/questionnaire.md。读取答案，只告诉我：还有哪些新的歧义或相互矛盾的地方。没有就说"没有"。
```

#### E2：门一——验收地基、合并并切出 `integration`

**层级：** 每项目｜**主负责：** 我｜**前置：** E1｜**下游：** E3

先做 1～5 的交接，再过门一（6～8），最后合并并切出 `integration`（9）。**首个项目由你在本机逐项确认。** 地基 PR 的提交号一变，前面的绿灯全部作废。

**② 动作**

1. 【我】收地基草稿 PR。
2. 【我】在本机先把 `migrate.yml` 单独推到已锁定的 `main`，以后由你从 `main` 手动触发并填入确认过的提交号（附录 B.5）。
3. 【我】本机检出 `stage-0`，将 `main` 的这次更新合进来，再把 `stage0/github/` 里其余文件移到 `.github/`，清掉暂存副本，用你的账号推回 `stage-0`。首次可以请另一家 AI 对照附录 B 核对这些文件。
4. 【我】等地基 PR 上构建及已接通的 CI 变绿。首次依赖数据库的检查留到迁移后验证。
5. 【我】从 `main` 手动触发 `migrate.yml`，填入地基 PR 当前提交号；迁移成功后，复核该提交的 CI，再看预览和 `/debug`。

**门一（合并前）：**

6. 【我】点 Vercel 预览确认外壳能打开，核对该提交的 CI 结果。**"绿"的定义：** 具名 CI 检查（`verify`、`guard`、Vercel 部署等）、Vercel 预览部署和最后的合并，必须对着**同一个 PR 提交号**。核对预览部署的提交号等于 PR 当前提交号，防止读到分支上的旧部署；合并时用 `gh pr merge --match-head-commit <提交号>`，提交号变了就拒绝【待验证】。
7. 【我】打开预览的 `/debug`，确认任务记录可见、样本数据能正常读写；匿名访问返回 404。**分三步判，避免平台保护层造成误判：** 先带 Vercel 放行密钥请求，确认请求已到达应用（是应用自己的响应，而不是平台的登录拦截页）；再用同样带放行密钥、但**没有应用登录态**的请求，期望 404；最后用有权限的账号，期望页面可用。第一步到不了应用，只说明预览被平台挡在外面，不算 404 通过【待验证】。
8. 【我】核对必备文件：`AGENTS.md`、保底版 `DESIGN.md`、主题变量、`.env.example`、`.ai/bin/setup-worktree.sh`、附录 B 的守卫及验收测试和交付开关。

**合并并切出 `integration`：**

9. 【我】在本机合并地基 PR 到 `main`（merge commit），再切出并推送 `integration`：

   ```
   git checkout main && git pull --ff-only
   git checkout -b integration
   git push -u origin integration
   ```

   确认 Vercel 生成 `integration` 预览；构建由 Vercel 完成，PR 的 `verify` 负责类型检查等。服务器以 `agent` 执行 `git fetch origin --prune`、`git rev-list --left-right --count HEAD...origin/main`、`git merge --ff-only origin/main`，确认副本干净，且 `origin/integration` 已有地基提交。

**③ 完成标准**

- [ ] 门一（6～8）通过：预览外壳能打开，CI 的"绿"对着同一个提交号，`/debug` 三步判定通过，必备文件齐全。
- [ ] 地基已合入 `main`。
- [ ] `integration` 已切出并有预览；服务器副本干净，且 `origin/integration` 已有地基提交。

**④ 出错怎么办**

| 现象 | 归谁 | 怎么处理 |
|---|---|---|
| 门一红了：规则集、权限、预览平台保护层这类问题 | 我 | 不进返修，由你处理 |
| 门一红了：代码问题 | AI | 按同一地基 PR 返修，最多 3 次；敏感工作流的改动仍由你推 |
| 提交号变了 | 我 | 前面的绿灯全部作废，重新核对 CI；迁移有变动时按附录 B.5 再执行 |
| 仍红 | 我 | 发卡点通知，停在门一 |

**⑥ 待验证**

- `gh pr merge --match-head-commit` 的行为【待验证】。
- `/debug` 三步判定里平台保护层的表现【待验证】。

## 0. 适用范围和使用者前提

适用：简单、确定性高、想做"大而全计划、一次性交给 AI 跑完"的项目（例如猫咪纪念网站）。

不适用：需求本身还没想清楚的项目；前端需要大量试错的部分（留到后面对话式打磨）；黑客松（本版不覆盖，方法要反着来）。

使用者前提（影响了全部取舍）：

- 非专业开发者，熟练 vibe coding，不读代码，靠预览链接、`/debug` 页和演示步骤验收。
- 第一目标是省力和速度，可以为效率牺牲一部分安全，token 充足。
- 先看到第一轮技术计划，才知道自己要什么配置，因此流程允许"业务问卷 → 技术草案与技术问卷 → 调方案 → 再定稿"。
- 板块之间的轻微依赖问题视为小问题，验收时再查；但公共契约与目录边界必须在开跑前锁死。
- 默认工具：Vercel + Supabase；中国项目用 AWS 分流 + 腾讯云服务器转入口；需要常驻在线的 AI 服务用 "grokbot"（具体指哪个产品尚未确认）。

## 1. 核心原则

**排期围绕"何时需要你"来排，因为你是整个项目唯一的瓶颈。** 无人值守时 AI 会停下，通常是这五种原因之一，每一种都要在开跑前处理掉：

| 停下的原因 | 例子 | 解法 |
|---|---|---|
| 缺接入 | 缺 .env.local、预览变量或 CI Secrets | 按附录 B.7 核对本机、服务器、Vercel Preview、GitHub Secrets 四处，做凭据冒烟 |
| 缺决策 | 用哪个外部服务？异常怎么兜底？ | 开跑前答完两轮问卷；运行中按 3.1 第 5 节选可逆方案、交给 AI 代决或搁置 |
| 缺权限 | 无界面 agent 遇到未授权命令 | D3 用 Cezar 的 smoke 图验证权限配置和超时，区分立即拒绝与等待输入 |
| 不知道算不算做完 | 做完一段就停下来问"可以吗" | 每个任务带机器能自己跑的自动检查（默认 Mock） |
| 模型自己收工 | 干十分钟就停 | 由服务器上的 Cezar 驱动：工作流图规定下一步，失败回环有上限（3.5） |

其余原则：

1. **状态写在文件里，不写在对话里，且并行不写同一文件。** 计划、接入清单、验收脚本放仓库；运行红线写进 `AGENTS.md`；并行决策拆成 `docs/decisions/<板块ID>.md`。
2. **问题一律变成卡片或清单条目**，不在聊天里零散修。
3. **不可逆/高风险操作由你亲手触发。** 真实扣费、主网交易、永久存储、对真实用户发信等永远不在无人值守运行中做；运行环境只放沙箱/测试密钥。
4. **审查防作弊、失败有熔断、CI 默认走 Mock。** 审查是软关卡，硬关卡由 GitHub 执行。verify 失败、CI 红、审查要求修改、合基线冲突合计最多修 3 次，再失败就熔断。自动测试默认走本地 Mock/沙箱桩，不打爆真实外部配额。
5. **前端留到后面打磨，但前期必须"锁插座、不锁长相"。** 后端并行期间用中性白胚房 + 语义化 token（含 `--font-heading`）+ 短小（不超过 40 行）的保底 `DESIGN.md` 锁死样式接口，禁止硬编码颜色和魔改基础组件；前端自动测试不做像素截图对比，确保后期换皮肤不动一行业务逻辑。
6. **硬关卡只在 GitHub，机器管得了的不靠文字。**（见附录 B）本地钩子和 AI 的权限设置都能被绕过，只用来提早反馈；真正的"没过检查就不能合并"由 GitHub 规则集 + CI 守卫执行。能用类型检查、lint、测试表达的规则，不写进 `AGENTS.md`。验收标准写成测试并锁定，worker 不能改。零豁免：不留 `eslint-disable`、`@ts-ignore`、`any`。
7. **每个红灯都要告诉 AI 下一步做什么。** 小决定自行记录，拿不准交给代决；"必须你"和无法在本板块做的事才搁置（3.1 第 5 节）。卡点能在独立决策文件和草稿 PR 找到，无关板块照常继续。

## 2. 阶段视图

行动清单的另一种看法：按阶段说明为什么这样排序。阶段编号与行动清单的 A～G 一致。

### 阶段 A：一次性底座（A1～A2）
- 云服务器、机器账号、工具登录、Cezar 和工作流模板包都与具体项目无关，做一次就能复用，所以单独成阶段。第一次做时可以穿插在 B～C 阶段之间，最晚在 D3 之前完成。
- 服务器的开机初始化脚本只装工具、建用户，不放令牌和登录信息。

### 阶段 B：开项目（B1）
- 初始化仓库时就锁死 `.gitignore` 并推 `main`，防止后续泄密。账号前提（私有仓库需 GitHub Pro）现在就定，免得规则集到后面才发现挡不住。
- 需求原话和手册副本都放进项目，新开的 AI 会话才看得到。

### 阶段 C：需求到计划（C1～C4）
- **C1：** 先用 `grill-me` 方式一次性把**产品与业务边界**问透；BMAD 只在想法尚未成形时用。
- 问卷里除了业务边界，还要问清内容权限（谁能看、谁能公开、能否撤回）和"四个小故事"（无权限、重复、中断、事后才发现），这些是你自己很难主动想到的。
- **C2：** 先让强模型给出第一轮技术方案、板块划分、地基产出和密钥清单，再答技术问卷并调方案。调好后请另一家模型做方向评审，再定稿。方案一确认就发起等待项（域名、备案、审核），缩短关键路径。
- **C3：** 用 **Superpowers 写计划**定稿（GSD 格式绑定自家执行器，BMAD 偏重）。定稿锁死：每板块范围/禁碰目录/验收标准、地基产出（含中性主题变量、保底 `DESIGN.md`、`/debug` 与 `AGENTS.md`）、Mock 测试分层（前端不做像素截图死对比）、`integration` 集成目标。
- 用**另一模型家族**做细节评审，只把需要你决定的条目交给你。改完按最终计划重生成并核对 `docs/modules.json`。
- **C4：** 接入清单和验收脚本都从最终计划派生，一次生成。

### 阶段 D：接入与锁仓（D1～D3）
- **D1：** **单开会话**配接入，避免琐碎步骤污染计划上下文；等待项（域名、备案、审核）已在 C2 发起，接入清单里排最前。本步做**独立凭据冒烟**。密钥按附录 B.7 分放本机、服务器、Vercel Preview、GitHub Secrets 四处；生产密钥物理隔离。
- **D2：** 推文档，先锁 `main`（及 `production-lock`），再邀请机器账号。
- **D3：** 邀请机器账号、克隆仓库、登记 Cezar、写入工作流和脚本。先在 `smoke-base` 冒烟，再完成 3.5.5 的第一组检查。

### 阶段 E：地基（E1～E3）
- **E1：** 先单任务交地基草稿 PR。
- **E2：** 你按交接把工作流移到位、执行迁移，过门一（预览、诊断、必备文件），在本机合并、切出 `integration`。
- **E3：** 启用 `integration` 规则集后过门二（最小真实链路与故意犯错演练），才开并行。

### 阶段 F：批量开发循环（F1～F2）
- **F1：** Cezar 和提交脚本都以 systemd 服务运行；确认重启能对账、登录有效、通知畅通后，启动该批服务，守前十五分钟再离开。
- 提交脚本按依赖和集成测试结果开工；失败按 3.4 重试与熔断。各板块写独立的决策文件，全部结束后先发摘要，再提交 `final-report`。
- **F2：** 读报告、决策和搁置原因，点 `integration` 预览验收，配合 `/debug` 读任务记录。发现问题就在驾驶舱或用提交脚本提交返修任务，复验到通过。

### 阶段 G：收尾（G1～G3）
- **G1：** 用真实内容先开 2～3 个平行试装分支真机对比选定皮肤，再单线程微调 `DESIGN.md` 与排版呼吸感，不动已有业务逻辑。
- **G2：** 选定的皮肤先合入 `integration` 并用手机再走一遍核心操作；过上线门禁（权限、`/debug` 关闭、测试/生产分库、失败提醒、备份恢复、预算上限）后合并生产，由你亲手配置生产密钥并触发不可逆操作。
- **G3：** 把卡点复盘回写进模板与 `docs/field-notes.md`。

### 3.1 仓库规则文件模板（`AGENTS.md`）

由板块 0（地基）生成并放进仓库根目录，确保每个新会话和审查 agent 自动加载。`AGENTS.md` 是多数 AI Agent 工具都认的通用文件名；如果你的工具只读自己的文件名（如 Claude Code 读 `CLAUDE.md`、Gemini CLI 读 `GEMINI.md`），就各放一个只写"读 `AGENTS.md`"的兼容文件，规则本体只维护 `AGENTS.md` 这一份：

```markdown
# Agent 运行规范

## 1. 目录所有权与禁碰红线
- 受保护路径以 `.github/protected-paths.txt` 为准，含脚本、工作流、测试输入、适配器公共接口和安全闸（B.2）。常规板块不改；需要变更时写进决策文件和 PR 的"需要地基变更"。
- 不擅自新增公共依赖；需要时按第 5 节处理。不引用其他板块目录里的代码。
- 每个板块只允许修改 `docs/plan.md` 中指明归属的目录和文件。
- 把样图、截图、调试输出等临时产物放在项目根目录下由 Git 忽略的 `local/`，按需建子目录；工具强制使用内置目录时，把结果复制到 `local/`，交付时提供项目内路径。
- 公共区域（数据库迁移、共享类型、全局配置、根 `package.json`、主题变量文件如 `globals.css`、`DESIGN.md`）仅归"板块 0：地基"或专门的装潢轮维护；日常并行板块严禁擅自修改。
- 缺公共依赖或共享契约时先在本板块找合规做法，不私建重复类型；找不到就声明需要决策，确认必须改共享契约时按第 5 节搁置。

## 2. UI 设计边界（锁插座、不锁长相）
- 创建或修改任何 `.tsx` 页面或组件之前，先读根目录 `DESIGN.md`（纯后端改动不用读）。
- 所有页面遵守根目录 `DESIGN.md`，使用既有语义化 token 与基础组件；机器检查的规则见附录 B.3。


## 3. 环境变量与测试分层
- 严禁将 `.env`、`.env.local` 或任何明文密钥提交进仓库或打印到日志。
- 自动测试与 CI 默认必须使用本地 Mock / 沙箱桩（确定、快速、零外部消耗），禁止在单元测试或 CI 重试中调用真实付费/限流/不可逆外部接口。
- 前端自动检查严禁做像素级截图死对比（只保留基础可用性、对比度与移动端防溢出等检查）。
- 严禁触碰任何生产环境或不可逆操作（真实扣费、主网交易、永久存储、对真实用户发信等）。

## 4. 验收命令
- 类型检查：`[例如 pnpm typecheck]`
- 单元测试：`[例如 pnpm test]`
- Vercel 部署构建：`[例如 pnpm build]`
- 不删除或弱化验收标准，不用 `git commit --no-verify`，不强推。
- 做完的定义：`pnpm verify` 全绿；只把 `e2e/acceptance/delivered/<板块ID>.json` 改为 true，本板块验收测试实际通过。提供四节 PR 描述：完成内容、决策、需要地基变更、卡点（无则写"无"）。
- 全量 e2e 只由 CI 跑。不要另写临时检查脚本，不要手动启动服务器到处点。

## 5. 无人值守规则与熔断
- **自己选：** 小决定选可撤回的，只写自己的 `docs/decisions/<板块ID>.md`。板块 ID 用小写英文加短横线。
- **AI 代决：** 拿不准就声明 `need_decision`，由工作流的 `decide` 处理，最多 3 次。代决仅在测试环境生效，必须可撤回；记下问题、选择、理由、备选和撤回办法，标"AI 代决"。
- **搁置：** 触及下方"必须你"或两种"做不了"时写明原因，由图记录、通知并以 needs-human 结束；无关板块继续。
- **必须你：** ① 开通、升级、充值或超预算；② 真实资金、主网、任何生产操作；③ 删数据或破坏性迁移（删表、删列、改列类型）；④ 给真实用户发消息、公开内容或放宽数据可见范围；⑤ 新外部账号、密钥或权限；⑥ 改守卫、CI、规则集或审查标准；⑦ 推翻你在问卷或计划里的明确答案。改数据库结构（首个项目含新增字段）或缺共享契约属于"做不了"，同样搁置。
- **熔断：** verify 失败、CI 红、审查要求修改、合基线冲突合计最多修 3 次。单次实现或修复超时由图处理。失败时记录卡点、报错和尝试过的做法；工作流负责推送、开草稿 PR 和通知。
- 合并目标是 `integration`。由工作流开 PR、同步基线、重跑检查和合并；worker 不自己开 PR 或合并，不 rebase，不强推。

## 6. 数据库、权限与外部回调红线
- 数据库的行级权限规则（如 Supabase RLS）不得关闭，也不得写成全放开（如 `USING (true)`）；新表默认开启，并按 `docs/plan.md` 授权。

- 迁移只追加：已在共享库（测试/生产）执行过的迁移文件不得修改；严禁对共享库执行 `db reset`、`DROP TABLE` 或清库。开发者自己的一次性本地库可以重置。
- 测试和生产是两个独立项目，只连测试项目。不使用 `supabase`、`vercel` 命令行。
- 高权限密钥（如 `SERVICE_ROLE_KEY`）只通过带 `import "server-only"` 的服务端文件使用，不进前端或 `NEXT_PUBLIC_*`。外部服务走适配器；主网仅在 `ALLOW_MAINNET=true` 时运行，自动环境一律不设。
- 对外开放的表单和接口（如订阅邮箱）要有输入校验和基本限流。
- `/debug` 与写入样本数据的入口：用 `VERCEL_ENV`（不要用 `NODE_ENV`，Vercel 预览环境的 `NODE_ENV` 也是 `production`）判断，仅非生产开放并加鉴权，生产返回 404。
- 外部回调（webhook）必须验签，并用事件/消息 ID 做唯一键去重；重复投递不得产生重复数据，也不得重复触发不可逆操作。
- 大文件（如手机原图）不得塞进单个同步接口：平台请求体有上限（如 Vercel 函数约 4.5 MB），改为直传存储或分步处理；耗时长的流程拆成可重试、可恢复的步骤，并记录状态。
- 处理失败要写入任务记录表（编号、时间、状态、简短原因）；不要把原文、照片或完整入参复制进日志。
- （仅项目含 AI 调用时）模型 ID 走统一配置，提示词集中存放，输出必须经格式校验并有失败降级；AI 拿不准时默认进"待确认"，不得自动做不可撤回的操作。
```

### 3.2 审查 Agent 检查清单

### 3.5 执行器：云服务器 + Cezar

需要跨板块维护接力时，用独立维护身份核对已授权的修复、PR 放行和后续派单。把权限边界和判断原则写进 `SOUL.md`，按实际发生的问题补充限制。维护凭据放在独立服务中，合并以仓库保护规则和对应授权为准。配置 Telegram 入口时，只接已授权的查询和维护指令。

**Cezar** 是开源的编排驾驶舱（MIT，Node 20+），在服务器上以系统服务运行，用你自己登录的 AI Agent 命令行干活（目前文档里提到的有 `codex`、`claude`，是否支持 Gemini 等其他工具【待核对】）。每个任务一个 git worktree，任务按工作流图执行（agent、检查、回环、人工关卡、开 PR、等 CI 等节点），有手机可用的驾驶舱和通知。它自称"从不自动合并"，所以合并这一步由我们在工作流图里补（3.5.2）。

新执行器**必须满足**下列 7 条要求，右侧是 Cezar 里的落实方式：

| # | 要求 | Cezar 里怎么落实 | 状态 |
|---|---|---|---|
| 1 | **落后分支谁来更新** | `sync` 合入远程基线，重跑 verify；检查合并结果，遇到落后、冲突或超时按 3.5.2 重新排队 | 【待验证】 |
| 2 | **失败重试上限** | verify 失败、CI 红、审查要求修改、合基线冲突共用 3 次修复。耗尽记录卡点再通知 | 【待验证】 |
| 3 | **审查 agent** | 不同模型家族，判 `approve`、`changes`、`human`。只有 `review.approve` 通往合并；GitHub 上仍是软关卡（3.9） | 【待验证】 |
| 4 | **新工作目录环境** | 从 `origin/<base>` 新开 worktree；`.ai/bin/setup-worktree.sh` 核对基线、复制测试环境文件并安装锁定依赖 | 【待验证】 |
| 5 | **密钥与登录**：worker 只拿测试环境密钥；机器上不登录 `supabase`、`vercel`；不设 `ALLOW_MAINNET`；Linux 优先开沙箱 | 见 3.5.1；Cezar 与 worker 同一系统用户，没法再做用户分离，硬关卡只有 GitHub 规则集 | 已知代价 |
| 6 | **并行线数** | 全服务器共用 `maxParallel`，从 2 开始，最多调到 3。配置位置暂按 `~/.cezar/config.json`【待验证】 | 记进 `docs/field-notes.md` |
| 7 | **执行器权限仅作提醒** | 不开"跳过全部权限确认"类模式，用非 root 和可用的沙箱。无界面拒绝行为见 3.5.5；硬关卡见附录 B.5、B.6 | 【待验证】 |

#### 3.5.1 服务器与账号

- **地区：** 选海外。先核对所用 agent 的支持地区和订阅账号用于服务器无人值守运行的条款【待核对】。
- **规格建议：** Ubuntu 24.04；4 核 / 8 GB 内存 / 80 GB 磁盘起。Playwright 和构建吃内存，实测后调整。
- **专用机：** 只放你自己的、只用测试密钥的项目，不放其他云平台的凭据。多项目用同一机器账号和系统用户，worker 能读其他项目的测试密钥、推其他已授权仓库；测试密钥有实际价值的项目单独开机。并行名额合计不超过 3。
- **用户：** 管理用户有 sudo，由它执行固定版本的 `npx cezar-run@x.y.z server-install --platform ubuntu-vps`。Cezar 与各 agent 用无 sudo 的 `agent`；安装器能否指定运行用户【待验证】。配不通时用用户级 systemd 加 linger，再配反向代理。
- **GitHub 令牌：** 机器账号只加到需要跑的仓库，给 Write，绕过名单只放你。经典令牌只勾 `repo`，服务器令牌永不带 `workflow` 或 Workflows 权限。同一机器账号可服务多个获邀仓库；fine-grained 能否用于个人仓库协作者【待验证】。有效期覆盖整夜。
- **登录：** 以 `agent` 登所选 AI 命令行；无界面方式和整夜续期【待验证】。GitHub 用机器账号令牌执行 `gh auth login --with-token`。以固定稳定版的 `cezar-run@x.y.z` 安装和提交，升级前先冒烟。
- **访问：** 驾驶舱只经 Tailscale 或 IP 白名单访问，加 HTTPS 和登录口令。能登入驾驶舱就等于能在服务器以服务身份执行任意命令。`CEZ_REMOTE_AGENT_ACCOUNTS` 不开。
- **仓库副本：** 每个项目登记 `~/projects/<项目名>`，留在干净的 `main`，只作 worktree 来源；用 `git fetch origin --prune` 更新远程引用，需要时 `git merge --ff-only origin/main`。若 Cezar 从副本工作区读图，须快进才能加载新版【待验证】。
- **环境变量文件：** 每个项目一个 `~/secrets/<项目名>.env.local`，权限 600，`.ai/bin/setup-worktree.sh` 只复制，不建软链。
- **绝不放：** 生产密钥、主网私钥和助记词、Supabase 访问令牌和数据库密码、Vercel 命令行登录、`ALLOW_MAINNET`。
- **开机自启：** Cezar 和提交脚本都注册为 systemd 服务（3.5.3）。

#### 3.5.2 工作流图模板

四张图放 `.ai/cezar/workflows/`，正文提示词放 `.ai/prompts/`（附录 B.2）。下面的节点类型、出口名、字段、模板变量都是示意【待验证】，按 3.5.5 校正。`runner` 用你选的工具，审查与干活用不同模型家族。`base` 同时指定新 worktree 的远程基线和 PR 目标：冒烟 `smoke-base`、地基 `main`，板块、返修和报告 `integration`。

**`module-delivery.yaml`**（板块和返修）

CI 等待先给 40 分钟，再按排队和实际部署耗时调整（套餐见 3.6）。`review` 载入 3.2 正文。批准的是 `ci` 记下的提交号。

```yaml
version: 2
name: module-delivery
params: [task, module_id, base]                 # base：integration（板块、返修、总报告）
budget: { usd: "[每个任务的上限]" }              # 字段名【待验证】
nodes:
  - { id: start, type: start }
  - { id: setup, type: check, command: "bash .ai/bin/setup-worktree.sh ." }   # 在已建好的工作树复制测试环境并安装锁定依赖
  - { id: implement, type: agent, runner: "[干活 agent]", timeoutMs: 900000, verdicts: [done, need_decision], prompt: "{{params.task}}" }   # 拿不准时声明 need_decision【信号方式待验证】
  - { id: verify, type: check, command: "pnpm verify" }
  - { id: retry, type: loop, max: 3 }           # verify 红、CI 红、审查要求修改、合基线冲突，四种合计
  - id: fix
    type: agent
    runner: "[干活 agent]"
    session: { continue: implement }
    timeoutMs: 900000
    verdicts: [done, need_decision]
    prompt: |
      上一步没有通过，或者刚拿到代决结果。先查清原因再修：
      - 本地检查输出：{{nodes.verify.output}}
      - CI：运行 gh pr checks 和 gh run view --log-failed 查看失败日志
      - 审查意见：{{nodes.review.summary}}
      - AI 代决结果（有的话照此执行）：{{nodes.decide.summary}}
      - 合并基线时的冲突文件：{{nodes.sync.conflicts}}
      修完保证 pnpm verify 通过。不要改测试、检查配置或受保护路径。
  - { id: commit, type: git.commit, message: "feat({{params.module_id}}): module delivery" }
  - { id: sync, type: git.sync-base, base: "origin/{{params.base}}" }
  - { id: reverify, type: check, command: "pnpm verify" }
  - { id: disarm, type: check, command: "bash .ai/bin/disarm-pr.sh" }   # 已有 PR：撤销自动合并、改回草稿；没有 PR：直接通过（B4）
  - { id: push, type: git.push }
  - { id: has_pr, type: check, command: "bash .ai/bin/has-pr.sh" }   # 已有 PR 返回 pass，没有返回 fail，查询出错返回 error（防止重复开 PR）
  - { id: pr, type: github.draft-pr, base: "{{params.base}}" }
  - { id: ci, type: check, command: "bash .ai/bin/wait-checks.sh 40" }   # 按当前提交号逐项核对 verify、guard、e2e、Vercel，并记下提交号
  - { id: ci_red, type: check, command: "bash .ai/bin/ci-red.sh" }       # 通过 = 确实有检查失败；失败 = 只是超时没出结果
  - id: review
    type: agent
    runner: "[审查 agent，和干活 agent 不同家族]"
    verdicts: [approve, changes, human]
    prompt: "[载入 .ai/prompts/ 下的 3.2 正文；核对 wait-checks 记录的提交号]"
  - { id: decisions, type: loop, max: 3 }        # 每个任务最多代决 3 次
  - id: decide
    type: agent
    runner: "[你能用到的最强模型，最好和干活 agent 不同家族]"
    verdicts: [decided, must_human]
    prompt: |
      你替用户做决定。先读 docs/plan.md、docs/questionnaire.md 和 .ai/prompts/must-human.md（"必须你"清单）。
      - 如果问题属于"必须你"清单，或属于两种"做不了"（改数据库结构、缺共享契约）：给出 must_human，并写明原因。
      - 其他情况：按计划和问卷的意图，选推荐的、能撤回的方案，给出 decided。
      把决定写进 docs/decisions/{{params.module_id}}.md，标"AI 代决"，写明问题、选择、理由、备选方案、怎么撤回。
      待决问题：{{nodes.implement.summary}} {{nodes.fix.summary}} {{nodes.review.summary}}
  - { id: ready, type: github.pr-update, ready: true }
  - { id: automerge, type: check, command: "bash .ai/bin/automerge.sh" }   # 合并时绑定 wait-checks 记下的提交号（B4）
  - { id: wait_merged, type: check, command: "bash .ai/bin/wait-merged.sh 45" }   # 45 分钟内合并就通过；落后、冲突或超时就失败
  - { id: requeue, type: loop, max: 3 }
  - id: writeup
    type: agent
    runner: "[干活 agent]"
    session: { continue: implement }
    prompt: "按失败记录约定先撤销自动合并并改回草稿。把卡点、报错和已尝试过的方案写进 docs/decisions/{{params.module_id}}.md，提交并推送。没有 PR 就开 draft PR。PR 描述写四节：完成内容、决策、需要地基变更、卡点。"
  - id: human_note
    type: agent
    runner: "[干活 agent]"
    session: { continue: implement }
    prompt: "按失败记录约定先撤销自动合并并改回草稿。这件事需用户白天处理。把事项、原因、你的推荐，以及'如果用户选择不做，后面怎么继续'写进 docs/decisions/{{params.module_id}}.md 和 PR 描述，提交并推送；没有 PR 就开 draft PR。"
  - { id: alert, type: notify.webhook, url: "${CEZ_ALERT_URL}", body: "{{params.module_id}} 卡住了，见驾驶舱" }
  - { id: alert_human, type: notify.webhook, url: "${CEZ_ALERT_URL}", body: "{{params.module_id}} 需要你决定，见驾驶舱" }
  - { id: ok, type: end, status: success }
  - { id: blocked, type: end, status: failed }
  - { id: needs_human, type: end, status: needs-human }
edges:

  - { from: setup.pass, to: implement }
  - { from: setup.fail, to: writeup }
  - { from: implement.done, to: verify }
  - { from: implement.need_decision, to: decisions }
  - { from: implement.fail, to: writeup }

  - { from: verify.fail, to: retry }

  - { from: fix.fail, to: writeup }

  - { from: commit.nothing, to: sync }
  - { from: commit.fail, to: writeup }

  - { from: sync.fail, to: writeup }

  - { from: disarm.pass, to: push }
  - { from: disarm.fail, to: writeup }

  - { from: review.approve, to: ready }          # 通往合并的唯一入口
  - { from: review.changes, to: retry }
  - { from: review.human, to: decisions }        # 先交给 AI 代决，不直接停

  - { from: decisions.exhausted, to: human_note }

  - { from: decide.fail, to: human_note }

  - { from: ready.fail, to: writeup }
  - { from: automerge.pass, to: wait_merged }
  - { from: automerge.changed, to: requeue }
  - { from: automerge.fail, to: writeup }
  - { from: wait_merged.pass, to: ok }
  - { from: wait_merged.fail, to: requeue }

  - { from: writeup.fail, to: alert }
```

几个检查脚本放在 `.ai/bin/`，由 D3 的 AI 写（3.10）：

- **`setup-worktree.sh <worktree-dir> [env-file]`**：工作流先核对基线，再从工作树根目录执行此脚本。脚本默认按原始克隆目录名取 `~/secrets/<项目名>.env.local`。目录名不同时可设 `CEZAR_WORKTREE_ENV_FILE` 指向该项目的测试环境文件。地基提供 `scripts/check-stage0.mjs --env-file <文件>`，校验成功后脚本才复制环境文件并按锁文件安装依赖。
- **`wait-checks.sh <分钟>`**：核对 PR 当前提交上的 verify、guard、e2e、Vercel 四个具名检查及各自来源。全绿才把提交号写到不提交的 `.cezar-head-sha`；失败、超时或查询错误写到 `.cezar-ci-result`。`ci-red.sh` 只在实际红灯时返回成功，超时或查询错误转卡点。查不到具名结果时保持红灯，不用汇总状态替代。
- **`has-pr.sh`**：用 `gh pr view --json number` 查本分支。查到返回 pass；确认不存在才返回 fail；其他查询错误返回 error，不当成没有 PR。
- **`disarm-pr.sh`**：确认没有 PR 才直接通过。已有 PR 时先撤销自动合并（`gh pr merge --disable-auto`），再用 `gh pr ready --undo` 转回草稿；在重新推送和卡点写回前都执行。查询错误停手，不当成没有 PR。
- **`automerge.sh`**：再次核对 PR 当前提交与审查批准的提交号一致，才用 `gh pr merge --auto --squash --match-head-commit <审查过的提交号>`【待验证】。提交号变化就撤销自动合并，回到同步、复查和重新审查；若验证发现自动合并不能绑定该提交，就只在四项全绿且 SHA 一致时尝试立即合并（仍用 `--match-head-commit`），否则留草稿，首夜不开这个自动合并入口。
- **`wait-merged.sh <分钟>`**：每 60 秒查 `gh pr view --json state,mergeStateStatus`。已合并返回成功；落后、冲突或到 45 分钟仍未合并就返回失败。再同步单独最多 3 次。到终点仍待合时先撤销自动合并、保留草稿。
- **失败记录**：`writeup` 与 `human_note` 把说明写进本板块决策文件，沿用现有 PR 或开草稿，更新四节 PR 描述。如果无法安全推送或 PR 已合并，就停在服务器写卡点到 `~/cezar-logs/<项目名>/blocker-log.md` 并通知；无法联网时留日志。PR 正文可由节点设置【待验证】，否则用 `gh pr edit`。重试修复上限和代决上限各自计数，预算、单步超时另计。
- **决策信号**：优先用 `need_decision` 结论；如果工具不支持，改为工作目录中不提交的 `.cezar-request.md`，用检查节点读取并清理【待验证】。`decide` 按 3.1 第 5 节和 `.ai/prompts/must-human.md` 判断，代决可撤回，只对测试环境生效。人工关卡只会原地等待，搁置则以 needs-human 结束并释放并行名额。

#### 3.5.3 任务提交与依赖顺序

D3 的 AI 把 `.ai/bin/submit-modules.sh` 配成以 `agent` 运行的 systemd 常驻服务，启动一批由你触发。系统级服务由管理用户安装；用户级服务由管理用户执行 `loginctl enable-linger agent`，再以 `agent` 用 `systemctl --user` 操作【待验证】。服务开机自启，断开 ssh 也能跑，用相应的 `journalctl -f` 看。已结束的批次不重复启动。

- **输入：** 只读 `origin/main` 上 C3 复核过的 `docs/modules.json`（`id`、依赖、可改路径），启动本批时记下该版本。
- **基线：** 提交前在 `~/projects/<项目名>` 执行 `git fetch origin --prune`；副本留在干净的 `main`，需要读新版工作流时先快进。任务以 `origin/<base>` 为起点【待验证】，板块开工再按 3.5.2 核对祖先关系。
- **提交：** 用固定版本 `npx cezar-run@x.y.z run` 或 Cezar HTTP 接口【待验证】。有依赖的要等上游 PR 合入，且含上游合并提交的 `integration` 版本全量 e2e 通过，才开工。记录集成测试提交号与结果。无依赖板块照常提交。
- **集成红灯：** 发通知，并按失败提交号建一次返修任务【待验证】。依赖板块继续等；超过时限（先设 60 分钟）标"跳过（集成测试未通过）"，写入报告。熔断和搁置只使依赖该板块的下游跳过。
- **运行台账：** `~/cezar-state/<项目名>/<批次>.json`，不进仓库。记板块 ID、状态（待提交、提交中、运行中、已合并、熔断、搁置、跳过）、Cezar 运行编号、PR 编号、上游集成测试结果。先记"提交中"再提交，接单后回填编号。同一批只由一个进程提交；台账用原子替换更新。
- **重启恢复：** 先对账台账、Cezar 按批次和板块 ID 查到的运行、GitHub PR【接口待验证】。已接单但没有 PR 的仍算运行中；对不上的发通知，不重复提交。
- **收尾：** 全到终态或总时限到（先设 12 小时）就发"全部结束"通知。把各板块结果、PR 链接、AI 代决条数和搁置原因同时写到 `~/cezar-state/<项目名>/<批次>-summary.md`；时限到时如实列出仍在跑的任务。正常收尾再提交一次 `final-report`，记下运行编号；报告任务失败仍有摘要。
- **备用合并脚本：** 仅在合并节点冒烟不过时启用。按 3.5.2 核对同一提交的四项检查、审查和 PR 状态，用 `--match-head-commit`；缺一项就留草稿。定时器和合并仍要经 3.5.5 验证。

#### 3.5.4 监听、通知与搁置

- **监听**由 Cezar 服务和 systemd 自动重启负责，提交脚本维护任务依赖和批次状态（3.5.3）。
- **通知：** Cezar 服务的环境文件里设 `CEZ_WORKFLOW_WEBHOOKS=1`，图只引用 `${CEZ_ALERT_URL}`。Telegram bot 的 `sendMessage` 地址含令牌，和 `chat_id` 一起只放服务器配置。直接发 `chat_id` 和 `text` 的格式【待验证】，必要时由 `~/cezar-bin/` 的转发脚本转发。只发到你自己的 `chat_id`，Telegram 不通时可选 Slack、Discord。
- **只发四类：** 卡点和需要你由图发，带任务参数里的板块 ID；全部结束由提交脚本发，附摘要；服务重启由 systemd 的启动通知发【待验证】。
- **搁置清单：** 以 3.1 第 5 节"必须你"和两种"做不了"为准。经 `decide` 后需搁置就记录、通知并以 needs-human 结束。早上在驾驶舱查这类已结束任务，按 F2 处理；只有依赖它的板块跳过。
- **（后续增强）双向与按钮：** 第一版做单向通知。以后用 Telegram 按钮回传选项时只响应自己的 `chat_id`，处理后另行提交任务。
- **额度用尽：** "额度重置后才启动"【待验证】。先记录报错，耗尽上限后按卡点处理。
- **manager 功能暂留：** 文档里只列一款 agent，第一版继续按 3.5.2 的图执行。

### 3.8 保底版 `DESIGN.md` 模板（风格未定时放根目录）

由板块 0（地基）直接放到仓库根目录。用可读的基础页面及示例或实际内容支持开发期验收，后续可在 G1 调整视觉。默认按 Tailwind + `shadcn/ui` 写法，换组件库时使用对应语义 token 与组件名。

```markdown
# 基础视觉规范

## 1. Current Stage Goal
- Clean, neutral, content-first layout. Focus on clear hierarchy and readability so real content can be evaluated without visual clutter.

## 2. Token & Typography Slots (`src/app/globals.css`)
- Use semantic tokens only (`bg-background`, `bg-card`, `text-foreground`, `text-muted-foreground`, `bg-primary`, `border-border`).
- Apply `font-heading` to all `<h1>`–`<h3>` titles and `font-sans` to body copy so heading fonts can be swapped globally later.
- Do NOT hardcode hex/RGB colors or arbitrary pixel spacing values in components.
- This file never contains concrete color values; exact values live only in `globals.css`.

## 3. Layout & Component Guardrails
- Build exclusively with standard `shadcn/ui` components without overriding their internal padding or border radius.
- Place at most ONE filled primary button (`<Button>`) per screen; use `variant="outline"` or `variant="ghost"` for secondary actions.
- Center main content (`max-w-3xl` or `max-w-5xl mx-auto px-4`), stack single-column on mobile, and implement empty, loading, and error states for every view.
- Do NOT add gradients, decorative backgrounds, custom shadows, or custom animations.

## 4. 首页与后台
- 公开内容页参考 Apple 的大图、字号层级与留白。首页显示项目标题和一个主要入口，适合用图时配一张贴合主题的大图。图文列表按内容组织，手机优先单列。
- 简单后台把待办、必要详情和主要操作放在一个工作页。多模块、多步表单或复杂权限场景可参考 Ant Design Pro 的导航、列表、表单和状态布局，沿用项目的设计变量。
- 有合适素材时优先用现有图片。缺首页主图时使用 `prompts/P-hero-image.md`。先生成一张，其他样图按验收页面补。用桌面和手机打开核心页面，确认主操作、图片裁切、空态和错误反馈。
```

**分工原则（"一本账"）：** `@theme`（`globals.css`）管"零件合不合格"，是机器硬卡尺，**具体数值（色号、圆角、字号）只存这里**；`DESIGN.md` 管"搭配好不好看"，是给 AI 的软说明，**只点名 token 代号、讲使用场景和红线，不抄色号**（例如写"`bg-primary`：每屏仅限 1 个主行动按钮"，不写 `#D97706`）。两边都写死色号，AI 会照抄成 `bg-[#xxxxxx]` 被 lint 打回，或者改了一边忘了另一边。只有 lint 没有 `DESIGN.md`，机器全绿也可能很难看（主色刷满整屏、一排五个主按钮）；只有 `DESIGN.md` 没有 lint，AI 过夜几轮就会忘词。

### 3.9 Stage 0 工程护栏（概述，规格在附录 B）

板块 0 按**附录 B** 实现（未实跑验证）。核心是四层防线：**L0 地基冻结**（外壳、设计变量、表结构与权限规则、适配器）→ **L1 `AGENTS.md`**（3.1）→ **L2 本地检查**（`pnpm verify`、lint 零豁免）→ **L3 GitHub 终审**（CI 的 verify 与 guard、预览站 e2e、数据库体检、规则集；唯一的硬关卡）。

附录 B 保留了**三处关键设计**：

1. **守卫不能被 PR 自己改掉。** guard 用 `pull_request_target` 触发，运行目标分支上的版本，只读文件名与板块开关，不执行 PR 里的任何代码；否则 worker 把 guard 改成"永远通过"，必过检查依然显示成功。E3 的演练 C5 包含这种情况。
2. **浏览器测试只能在测试预览站运行。** e2e 的触发条件限定部署环境为 Preview，目标网址缺失就停；正式站发布后只跑只读检查。因为验收测试会写入并清理样本数据。
3. **板块开关要核对"真跑过"。** 守卫按文件检查 `e2e/acceptance/delivered/<板块ID>.json`（已是 `true` 的要保留）；e2e 要求各已交付板块的用例实际通过且未跳过。首页健康始终运行。

另外两点落地时的选择：
- **停手记录：** 按 3.1 第 5 节处理，决策和卡点记在 `docs/decisions/<板块ID>.md`；草稿 PR 另附卡点及地基变更需求。
- **审查 agent 与合并：** 首个项目把审查当软关卡。worker 和 Cezar 同一用户，能修改服务器上的图、配置或自行执行合并命令。因此图内审查防的是无意越界，硬关卡由 GitHub 规则集和 CI 守卫执行。稳定后再评估把审查移到 GitHub Actions 并设为必过检查（记进 `docs/field-notes.md`）。

## 4. 术语

- **审查 agent**：独立的第二个 AI，按 3.2 或 3.2b 审查；结论指向它审过的提交。
- **worktree**：同一个仓库的多个独立工作目录，每条工作线一个，互不干扰。注意它不会自动复制被 `.gitignore` 忽略的 `.env.local`。
- **`integration` 分支**：并行板块、返修和报告的合并目标；Vercel 做构建并给预览，合入后全量 e2e。验收通过后由你合入 `main` 发布。
- **`/debug` 诊断页**：极简内部页面，用 `VERCEL_ENV` 判断环境并加鉴权，生产返回 404。读任务记录表，按编号展示时间、状态和简短原因；样本数据通过独立的同等级受控入口写入。
- **受保护路径 / guard**：`.github/protected-paths.txt` 列出公共配置、脚本、工作流、安全闸、测试输入等（完整清单见 B.2）。GitHub 守卫按目标分支的清单检查，不设标签豁免。
- **板块开关**：`e2e/acceptance/delivered/<板块ID>.json`，每块一文件。由地基预建，worker 交付时开启自己的开关，之后用例必须通过。
- **预览链接**：Vercel 为每个分支自动生成的临时网址，你点开就能验收。
- **无人值守运行**：你离开后，由云服务器上的 Cezar 按工作流图驱动 AI 把整份计划跑完的这段时间。什么时候跑都一样。
- **Cezar**：开源的编排驾驶舱，在服务器上以系统服务运行，调用你自己登录的 AI Agent 命令行（Codex、Claude 等）干活。它是本方案里的"监听程序"。
- **驾驶舱**：Cezar 的网页界面，手机和电脑都能用；看任务进度、已搁置的任务和费用。
- **工作流图**：`smoke`、`foundation-delivery`、`module-delivery`、`final-report`，见 3.5.2。新 worktree 用 `origin/<base>` 起步。

## 7. 并行和 worktree 规则

worktree 本身防止干活时互相干扰。会出问题的是环境变量缺失、合并冲突、共享契约变更和外部资源争夺。

**环境变量传递：**

- `git worktree` 不会复制被忽略的 `.env.local`。地基提供 `.env.example` 和 `.ai/bin/setup-worktree.sh`，从本机指定环境文件或服务器 `~/secrets/<项目名>.env.local` 复制，不建软链；其余落点按 B.7。

**合并冲突与共享契约的预防：**

- 地基先单独做完，大家共用的东西（核心依赖包、表结构、共享类型、数据契约）在并行开始前定好。
- 每个板块的目录归属写进计划，审查按计划核对；受保护路径由 GitHub 守卫检查。
- **禁止多个 worker 共写同一个文档**：只更新自己的 `docs/decisions/<板块ID>.md`，总报告由 `final-report` 汇总。
- **公共文件变动策略**：缺共享契约按 3.1 第 5 节走代决；确认需要改公共文件时搁置，由地基轮补后重新提交。
- **施工与装潢分离（设计文件只读锁）**：严禁在并行开发新功能的同一轮里，顺手让各分支"自由美化界面"。日常并行功能轮次中，主题变量文件（如 `globals.css`）和 `DESIGN.md` 始终只读；中后期想调皮肤或排版，单独开一轮单线程的装潢任务（或 G1 的临时试装分支），验收合入主干后，下一批并行分支自动继承新标准。
- 真出现普通合并冲突时，应退回给负责的 worker 自己解决。

**worktree 管不到的共用资源与测试分层：**

- 每个真实外部资源（如测试库迁移、测试邮箱、测试钱包等）只指定唯一一个负责板块，其他板块一律用样本数据。
- **更关键的是测试分层**：即便是负责该外部资源的板块，其单元测试和 CI 自动检查也默认走本地 Mock / 沙箱桩，**不在高频自动重试中真实消耗配额、发邮件或发链上交易**；真实调用只在"凭据冒烟（D1）"和"人工验收（F2）"触发。

**其他：**

- 先并行不超过 3 条线（stage0 的设计前提），E3 演练通过、实际跑稳后再考虑增加；超过 3 条时需要补附录 B.8 里"按板块的目录归属检查"。
- 并行线数的上限还取决于模型额度，同时跑的线数越多，消耗约是单条的相应倍数。
- 清理旧 worktree 和分支前，用台账确认任务已结束，成果已推送并能从 GitHub 找到。
- 某条线做乱了，丢掉那个分支，只重跑那个板块。

### B.1 要防的五类故障

1. **共享文件冲突**：多个分支同时改根布局、全局样式、锁文件、迁移。→ 地基冻结 + 受保护路径守卫。

4. **环境与无沙箱问题**：新工作目录缺 `.env.local` 和依赖；worker 能用机器上已登录的工具。→ 3.5 第 4、5 条。

### B.5 CI 工作流

**`.github/workflows/ci.yml`** 在 PR 的确切提交上运行 `pnpm install --frozen-lockfile`、`pnpm verify` 和 `pnpm secrets`。Vercel 部署负责构建检查。

**`.github/workflows/guard.yml`** 用 `pull_request_target` 检出受保护目标提交。按该提交的 `docs/modules.json` 核对板块 ID、可写路径和开关。首页、维护首页和工作器入口的例外由所属板块在可写路径里列出完整文件名，板块之间要有唯一归属。常规板块只能向 `integration` 交付。守卫只访问 PR 的 Git 对象，结果绑定 PR 的完整头提交号。试装和地基共有修订由维护者核对确切提交后按 B.6 放行。

**`.github/workflows/e2e.yml`** 根据 GitHub 部署记录确认测试部署来源，再检出该提交并跑 Playwright。仓库 Actions 变量按该文件配置测试 Vercel 的环境名、项目 ID、发出部署的账号 ID、项目 slug 和部署域名后缀。对受保护测试预览使用仅能放行测试站的凭据。地基提供 `scripts/d1-probe.mjs schema` 和 `e2e/support/check-delivered.ts`。板块 PR 运行锁定验收及本板块用例，`integration` 合入后等测试迁移状态，再跑全部用例。`e2e-status.yml` 独立核对部署来源并按提交号发布 `e2e` 状态。

**`.github/workflows/db-advisors.yml`** 在 `main` 使用 `db-admin` 的测试项目标识和 Advisor 读取令牌，从 Supabase 管理接口取安全体检结果。出现 error 或读不到有效结果则失败。支持手动、定时和从迁移工作流调用。

**`.github/workflows/migrate.yml`** 从 `main` 由维护者手动启动，填写独立核对过的提交号和 PR 编号。在仓库 Actions 变量中配置 `MAINTAINER_GITHUB_LOGIN`，测试地基首次启动前再填独立核对过的 `REVIEWED_MIGRATION_SHA`。先跑本地 PostgreSQL 复验，再由只允许 `main` 的 `db-admin` 环境执行。模板数据库角色和 schema 使用 `business_test`、`business_prod` 两个隔离范围。地基提交一份 `YYYYMMDDhhmmss_foundation_schema.sql`、一份 `supabase/seed.sql` 和已核对的数据库类型。测试种子只用字面量和可重跑的 `INSERT … ON CONFLICT … DO NOTHING`，无初始数据时可用空文件。已应用迁移只追加。现成的项目若已用不同的 schema 名称，由维护者在启用工作流前按既有名称核对迁移脚本和角色。

**`.github/workflows/migrate-integration.yml`** 在 `integration-merged.yml` 成功后，从可信主分支核验合并链，复验并只对测试 schema 应用增量。工作流把已验证的类型和 `integration-schema` 状态绑定完整提交号，供合入后 E2E 使用。首次维护者确认的测试地基迁移由手动工作流完成。

**`.github/workflows/prod-readonly.yml`** 供 G2 手动触发。在仓库的 Actions 变量中添加 `PRODUCTION_ORIGIN`，填正式站的 HTTPS origin。先用有权账号确认一条合成私密样本确实可读，把它的路径填入 `PRODUCTION_PRIVATE_PROBE_PATH`。在 Actions 运行 **Production read-only smoke**，核对首页 2xx、`/debug` 404，以及游客查看私密样本时的 401、403 或 404。三个检查均为匿名 GET。G2 可在验过一次后配置上线事件或定时触发，并核对 Actions 的失败通知。

### B.6 GitHub 与 Vercel 设置（人来做；板块 0 的 AI 写成"点哪里"的分步说明放进 `docs/stage0-report.md`）

- **GitHub 账号**：私有仓库需要 GitHub Pro，否则规则集不生效；或把仓库设为公开。
- **Settings → General**：开 Allow auto-merge、squash 和 merge commit；合并后可自动删功能分支。
- **`integration` 规则集**：E3 新建。禁止删除与强推，必须经 PR（审批数 0），只允许 squash【待验证】；必过检查 verify、guard、e2e、Vercel，并核对来源。关闭"合并前必须基于最新分支"；绕过名单只有你本人。
- **`production-lock` 规则集（临时生产分支）**：D1 把 Vercel 生产分支暂设为不存在的 `production`，但 `main-lock` 只保护 `main`。如果之后有人创建并推送 `production`，可能触发生产部署【待验证】。所以在授予机器账号写权限之前，对名为 `production` 的分支建这条规则集：限制创建、更新和删除，绕过名单只有你本人（GitHub 规则集有"限制创建"一类规则【待验证】）。G2 把生产分支切回 `main` 后可以删除。
- **`main-lock` 规则集**：D2 推完文档后先建，D3 邀请机器账号前确认生效。限制更新（含合并 PR），禁止删除和强推，绕过名单只有你。E3 保留该限制并补必过检查、只允许 merge commit【待验证】，也关 strict。发布由你从 `integration` 合入。
- **GitHub Secrets**：仓库级只放不敏感值，唯一接受的例外是预览放行密钥（见 B.7）；数据库管理凭据只进 `db-admin`，限定 `main`。
- **Vercel**：在浏览器关联仓库、生成自动化放行密钥，生产分支先用暂不存在的分支，G2 再设 `main`【待验证】。Preview 只用测试项目，自动验收默认走 Mock；实链路用测试配置，不设 `ALLOW_MAINNET`。

| 变量 | 本机 `.env.local` | worker（服务器环境或服务配置） | Vercel Preview | GitHub Secrets / Environment |
|---|---|---|---|---|
| Supabase 网址与匿名 key（测试项目） | 有 | 有 | 有 | — |
| Supabase 高权限密钥（测试项目） | 按需，仅服务端 | 按需，仅服务端 | 按需，仅服务端 | — |

| `VERCEL_AUTOMATION_BYPASS_SECRET` | — | — | — | 仓库级，供 CI 访问测试预览 |

### B.8 暂不做（过度工程的刹车）

**试跑暴露对应问题后再加：** Knip（孤立文件和多余依赖）；板块之间互相引用的目录规则（eslint-plugin-boundaries）；按板块的目录归属检查（并行超过 3 条线时）；Stop 钩子；本地提交钩子（lefthook）；前端定稿后的截图比对；Renovate、Lighthouse CI；Prettier。
